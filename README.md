# QuestOps

QuestOps is a Unity game-development Agent project for **verified quest authoring**. The RC1 scope is intentionally narrow so every important claim can be backed by executable evidence.

## RC1 workflow

```text
Browser quest request
  -> local FastAPI boundary
  -> real DeepSeek Harness session
  -> read-only project contract + authoring Skill tools
  -> strict JSON draft
  -> deterministic validation
  -> draft SHA256
  -> explicit human approval bound to that hash
  -> create-only apply
  -> Unity EditMode + PlayMode on the applied bytes
  -> exactly-once outcome verification
  -> auditable evidence chain
```

The canonical case is: **Level 5 → `npc_blacksmith_01` → collect `item_iron_ore` ×3 → return → receive 100 gold exactly once.**

## What is already evidenced in GitHub Actions

- Python deterministic tests and verification-tool regression tests.
- React/Vite tests and production build.
- Published `deepseek-harness-sdk` / runtime installation.
- QuestOps Harness plugin installation and composed-profile verification.
- Harness adapter software tests.

These are software/integration checks, not a claim that a live model or Unity Editor has executed.

## External release gates

The following remain external until their real evidence exists:

- **Harness Live:** requires a valid `DEEPSEEK_API_KEY`.
- **Unity EditMode / PlayMode:** requires an activated Unity **6000.3.23f1** Editor.
- **Full E2E:** requires both resources in one run plus explicit human approval.

The repository contains fail-closed runners for all three. A fixture cannot become live-model evidence, and Unity source presence cannot become Unity execution evidence.

## Local quick start

Requirements: Python 3.12 and Node 22.

```bash
python questops.py doctor
python questops.py setup
python questops.py serve
```

Open `http://127.0.0.1:8765/`. Fixture mode is safe and explicitly labeled as not a model call. Live mode requires explicit consent and a server-side API key; the browser never receives the key and has no approval/apply endpoint.

## Playable graybox

The Unity package contains a small playable graybox: WASD movement, E interaction, a blacksmith, three iron-ore nodes, HUD, reward and duplicate-reward protection.

With Unity 6000.3.23f1 installed:

```powershell
py -3 tools/unity_preflight.py --unity "C:\Program Files\Unity\Hub\Editor\6000.3.23f1\Editor\Unity.exe" --project .
py -3 tools/build_unity_demo.py --unity "C:\Program Files\Unity\Hub\Editor\6000.3.23f1\Editor\Unity.exe" --project .
```

Then open `Assets/QuestOpsDemo/QuestOpsDemo.unity` and enter Play Mode. The scene is generated by the Editor so the repository does not depend on opaque binary assets. Unity's Editor scene-management APIs are intended for this kind of edit-time scene creation and saving.

- `.github/workflows/rc1-e2e.yml`: real Harness → explicit approval → create-only apply → Unity → full evidence-chain verification.

See `docs/RUN_REAL_GATES.md` for exact prerequisites.

## Agent benchmark

`evals/cases.jsonl` contains 30 frozen cases: 10 valid paraphrases plus 5 each for missing requirements, unknown resources, unsupported gameplay, and requirement drift. `evals/run_eval.py` runs them through real DeepSeek Harness sessions and automatically scores decision correctness, strict draft validity, required tool use, and least-privilege tool surface.

The benchmark is intentionally credentialed and is available as the manual `agent-eval.yml` workflow. Without a real API key, only the dataset/schema tests run; no benchmark success rate is claimed.

## Evidence policy

- software unit tests ≠ Agent benchmark success;
- fixture/offline flow ≠ real model call;
- source inventory ≠ Unity execution;
- PASS requires evidence;
- model-generated changes cannot approve themselves;
- apply is create-only and receipt loss is recovered through hash-based reconciliation.

## Scope freeze

Until RC1 Full E2E is green, QuestOps does **not** add MCP, A2A, multi-agent orchestration, Agentic RL, long-term learning memory, a second quest type, or extra game systems.
